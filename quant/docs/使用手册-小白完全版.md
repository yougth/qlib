# 第 0 章 先看这里（3 分钟自检）

## 0.1 三件最容易踩死的事

**① 用错 Python 解释器 —— 100% 会踩**

本机现在有多个 Python，只有 **`/usr/bin/python3`** 装齐了全部依赖：

| 解释器 | numpy | qlib | xgboost | lightgbm | catboost | torch | 能用吗 |
|--------|-------|------|---------|----------|----------|-------|--------|
| `/usr/bin/python3` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | **✅ 用这个** |
| `/opt/homebrew/bin/python3`（→3.14） | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ 全崩 |
| `/opt/homebrew/bin/python3.11` | ✅ | ✅ | ❌ | ✅ | ❌ | ❌ | ❌ 缺一半 |

`PATH` 里 homebrew 排在前面，所以你直接敲 `python3` 会命中 3.14 然后报
`ModuleNotFoundError: No module named 'numpy'`。**README 里所有 `python3 xxx` 的写法今天都跑不通了**，全部要换成 `/usr/bin/python3`。

建议在 `~/.bashrc` 里加个别名，一次解决：

```bash
alias qpy='/usr/bin/python3'
```

之后本文档里的 `/usr/bin/python3` 都可以写成 `qpy`。

**② 忘了 `PYTHONPATH=.`**

`core` 是个本地包，不加 `PYTHONPATH=.` 会报 `ModuleNotFoundError: No module named 'core'`。所有命令都必须在 `qlib/quant/` 目录下、带 `PYTHONPATH=.` 运行。

**③ 直接相信 `outputs/` 里现成的数字**

`outputs/` 里的结果是 7 月 29–31 日跑的，而 7 月 31 日晚发现并修复了**两个会让收益虚高的严重问题**（见 [第 9 章](#第-9-章-当前已知的两个坑必读)）。**所有历史结果都需要重跑后才能相信。** 这是你接手后要做的第一件事。

## 1.2 三条主线的分工

系统里有**三种完全不同的"跑模型"**，新手最容易搞混：

| | 引擎① 自研滚动 | 引擎② 全模型基准 | 引擎③ 上线 |
|---|---|---|---|
| 入口 | `run_rolling.py` | `run_benchmark.py` | `live/train_annual.py` |
| 模型 | 只有 XGB / LGB / ENS | qlib 全部 14 个 + 3 个对照 | 你指定 1 个 |
| 训练器 | 自研 **RankIC 早停** | qlib 原生（**RMSE 早停**） | qlib 原生 |
| 特征 | 172 列 **+ 5 个 FCF 因子** | 172 列（**不注入** FCF） | 172 列（同基准） |
| 目的 | 出主结果 | 比"哪个模型架构强" | 冻结模型给实盘用 |
| 会存模型文件吗 | ❌ 跑完丢 | ❌ 跑完丢 | ✅ 存 pkl + manifest |
| 耗时 | ~30 分钟 | Phase A 数小时 / Phase B 数小时 | 单模型分钟~小时 |

> ⚠️ 引擎①和②的数字**不能直接比**：引擎①多了 5 个基本面因子且用 RankIC 早停，引擎②是纯 Alpha158 + RMSE 早停。要比较必须同引擎同口径。这是历史上写错过的坑。

# 第 2 章 系统是怎么工作的

## 2.1 一句话版本

> 每个月最后一个交易日，从"连续十年自由现金流和净利润都为正"的几百只股票里，用模型给每只打一个分，买分数最高的 10 只，等权持有一个月，下个月再来一次。

## 2.2 八步流水线（每步对应代码位置）

```
① 行情数据      ~/.qlib/qlib_data/cn_data_fixed        core/data.py
       ↓
② 股票池        十年双正 + year-2 规则                 core/universe.py
       ↓
③ 特征          172 列（+5 基本面）                    core/features.py
       ↓
④ 标签          未来 20 天涨幅，按日截面标准化           core/dataset.py
       ↓
⑤ 切分          train / valid / test（带 purge 间隔）   core/universe.py
       ↓
⑥ 训练          在 train 学，用 valid 早停             core/models.py
       ↓
⑦ 打分选股      月末打分 → 过滤不可交易 → 取 Top10      core/tradability.py
       ↓
⑧ 回测          T+1 成交，往返成本 0.4%                core/backtest.py
```

### ② 股票池：为什么是"year-2"

`core/universe.py` 的 `build_dynamic_universe(Y)`：只用 **Y-11 到 Y-2** 这十年的财报判定，**Y-1 年的数据一律不用**。

为什么？因为 Y-1 年的年报要到 Y 年 4 月底才披露。如果你在 Y 年 1 月选股时用了 Y-1 年报，就是用了当时还不存在的信息 —— 这叫**前视偏差**，是量化回测最经典的作弊方式。

入池条件（`build_dynamic_universe`）：
- 十年里 FCF（自由现金流）**每一年都 > 0**
- 2016 年起净利润**每一年都 > 0**
- 允许 20% 年份数据缺失（"覆盖 ≥80% 年份即可入池"）
- 池子不足 50 只（`MIN_POOL`）直接报错

池子大小随年份变化（来自 Phase B 日志）：W2020 137 只 → W2023 226 只 → W2026 303 只。

### ③ 特征：172 列是怎么来的

| 来源 | 数量 | 说明 |
|------|------|------|
| qlib `Alpha158` | 158 | 内置经典量价因子库（KMID/ROC/STD/RSQR/CORR/…） |
| `Alpha158Enhanced` 扩展 | 14 | 长周期（120/240 日）动量、均线、波动、量价相关 |
| **合计（基准 & 上线用）** | **172** | 工具实测打印 `特征列 172 个` |
| FCF 基本面因子 | +5 | **只有 `run_rolling.py` 会注入** |

那 14 个扩展因子（`core/features.py` 第 18–35 行）：

```
ROC120 ROC240      120/240 日涨跌幅（长周期动量）
MA120  MA240       价格 / 120·240 日均线（偏离度）
STD120 STD240      120/240 日波动率
BOLL60 BOLL120     价格相对 60·120 日均线的标准差倍数（布林位置）
VMA120 VMA240      成交量 / 120·240 日均量（长期缩放量）
CORR_PV20/60       价量相关性（量价配合）
VRATIO_5_60/5_120  5 日均量 / 60·120 日均量（近期放量倍数）
```

5 个 FCF 因子（`load_fund_features`）：`F_fcf_growth`、`F_profit_growth`、`F_fcf_profit_ratio`、`F_fcf_avg_3y_norm`、`F_fcf_cv_3y`。**严格 PIT**：Y 年年报的因子从 `Y+1-05-01` 才生效，且按日截面 MAD-zscore（不用全局标准化，避免时间泄露）。

### ④ 标签：模型到底在学什么

```python
DEFAULT_LABEL = ["Ref($close, -20) / $close - 1"]   # core/dataset.py:19
```

`Ref($close, -20)` 是 20 个交易日之后的收盘价，所以标签 = 未来 20 天（约一个月）的涨幅。

然后 `CSZScoreNorm` 把标签**按日做截面标准化**：同一天所有股票的涨幅减去当天均值、除以当天标准差。

**这一步很关键**：它意味着模型学的不是"这只股票会涨多少"，而是"**同一天里谁比谁涨得多**"。整体大盘涨跌被抹掉了，模型只负责排序。这也是为什么全系统的核心指标是 RankIC（排序相关性）而不是预测误差。

### ⑤ 切分：purged split（2026-07-31 刚改过）

`build_windows()` 产出 7 个窗口（W2020 ~ W2026）。以 W2026 为例：

```
train  2021-01-01 ~ 2024-11-30    ← 学习
       └─ 2024-12 整月留白（purge gap）
valid  2025-01-01 ~ 2025-10-31    ← 早停 / 选模型
       └─ 2025-11 整月留白（purge gap）
test   2025-12-01 ~ 2026-06-30    ← 出信号，绝不参与训练
```

**为什么每段末尾要空一个月？** 因为标签需要样本日之后 20 个交易日的价格。如果 valid 直接到 11-30，那 valid 最后 20 天样本的标签落在 12 月（也就是 test 段）里 —— 早停用的 valid 分数就偷看了测试期的价格。这叫 **label horizon 泄露**，是真穿越。

> ⚠️ `core/universe.py` 的文件头写得很直白：**旧代码里"12 月留白"的说法是错的**，12 月恰好是 test 段第一个月，留白从未存在。这个 bug 影响了 `outputs/` 里**所有**历史结果。详见 [第 9 章](#第-9-章-当前已知的两个坑必读)。

校验函数 `assert_purged()` 用**真实交易日历**验证，不再靠日期字符串长相判断。

### ⑦ 可交易过滤：为什么选出来的股票会被剔掉

`core/tradability.py` + `core/config.py`：

| 过滤 | 规则 | 为什么 |
|------|------|--------|
| 一字涨停 | 当日 `high == low` 且涨停 | 买不进去 |
| 停牌 | 无成交 | 买不进去 |
| 流动性 | 20 日均成交额 < 2000 万（`LIQ_THRESHOLD`） | 冲击成本太大 |

候选不足 `MIN_CAND = 20` 只时，这个月直接跳过（不调仓）。

### ⑧ 回测口径

| 项目 | 值 | 位置 |
|------|-----|------|
| 持仓数 | 10（`TOPK`） | `config.py:24` |
| 权重 | 等权 | `backtest.py` |
| 成交时点 | 信号日次一交易日（T+1） | `backtest.py` |
| 交易成本 | 单边换手 × 0.4%（`FEE_ROUNDTRIP`） | `config.py:25` |
| 一年交易日 | 244 天 | `backtest.py:52` |
| 回测区间 | 2020-01-01 ~ 2026-07-23 | `config.py:58,60` |
| "剔2020"起点 | 2021-01-01（`ALIGN_START`） | `config.py:59` |

### 自研训练器的特别之处（`core/models.py`）

**RankIC 早停**：qlib 原生用 RMSE（预测误差）早停，但标签已经按日标准化过、均值为 0，模型越学会排序、预测值越偏离 0，RMSE 反而变大 → 早停在第 1 轮就停了，模型退化成常数。这就是"**考试考错了科目**"。

自研版用 `RankICEval` 每轮算 valid 日度 RankIC，取最大值早停：

```python
N_ROUNDS, EARLY_STOP = 1000, 100      # 最多 1000 棵树，100 轮不涨就停
```

**三道保险**：
1. `best_iter < 30` → 自动用 2 套备选超参重训，按 valid RankIC 择优（**只用 valid，绝不碰 test**）
2. `check_convergence()`：`best_iter <= 0` 直接 `raise RuntimeError`，拒绝把退化模型混进结果
3. `best_iter < 30` 或 `valid RankIC < 0.01` → 高亮告警

## 3.2 引擎②：全模型基准

### Phase A（单切分初筛，回答"哪个模型架构强"）

```bash
# 全部 17 个（含对照系），每个最多跑 45 分钟，超时记 timeout
PYTHONPATH=. /usr/bin/python3 run_benchmark.py

# 只跑指定几个
PYTHONPATH=. /usr/bin/python3 run_benchmark.py --phase A --models XGBoost,LightGBM,CatBoost

# 放宽单模型预算到 2 小时
PYTHONPATH=. /usr/bin/python3 run_benchmark.py --phase A --models TCN --budget 7200
```

Phase A 用**一个固定切分**（`config.BENCH_SPLIT`）：train 2016–2021 / valid 2022 / 信号段 2022-12 ~ 2026-06，股票池按 2023 规则冻结。

关键工程设计：
- **每个模型跑在独立子进程** + wall-clock 预算。超时记 `timeout`、报错记 `failed`，**绝不静默跳过**
- pytorch 模型强制 `OMP_NUM_THREADS=1`（macOS 上 libomp 双加载会**无 traceback 段错误**）
- 产出：`outputs/_bench_{模型名}.json`（单模型）+ `outputs/benchmark_phaseA.csv`（排名）

| 参数 | 作用 | 建议 |
|------|------|------|
| `--models` | 模型列表（逗号分隔） | Phase B 必填 |
| `--tag` | 输出文件后缀，**隔离不同实验批次** | **强烈建议每次都带**，否则互相覆盖 |

这条线跟研究线完全分开，多了一层"**冻结**"：模型训练完存成文件，配上三重身份证，之后每月出单**直接加载不重训**。

```

|------|------|------|
| `--model` | `DoubleEnsemble` | 上线主力就是它 |
| `--year` | **必填** | 用哪个滚动窗口（`W{year}`）的分段训练 |

| `--verify` | 关 | 再训一遍比对，`差异 > 1e-10` 就 `raise` 禁止上线 |

### 冻结的三重凭证（`core/pipeline.py`）

每个冻结模型旁边有个 `manifest.json`，记录：

| 凭证 | 作用 | 不匹配时 |
|------|------|---------|
| **SHA256** | pkl 文件指纹 | 报"模型文件已被修改!" |
| **config_hash** | 模型超参 + TOPK + label_horizon + fee + liq 的哈希 | 报"冻结模型已失效 → 必须重新年度训练" |
| **git commit** | 代码版本 | 供追溯 |

manifest 里还存了训练时用的 `universe` 和 `segments`。推理时（`predict_frozen`）train/valid 分段**逐字取自 manifest**，只把 test 段换成最新区间 —— 保证特征标准化的拟合基准跟训练时完全一致。

> **这个机制的实际意义**：你只要动了 `config.py` 里那几个关键常量（比如把 `TOPK` 从 10 改成 15），`config_hash` 立刻变，下次出单会直接拒绝加载旧模型。**它替你记住了"改了配置必须重训"这件事。**

    [XGB W2026] best_iter=412, valid RankIC=0.0431 → OK      ← ⑥ 收敛诊断（最重要）
```

| 行 | 门槛 | 不达标会怎样 |
|---|------|-------------|
| ③ 行情覆盖率 | < 95% | **直接 raise 拒绝回测**（存活偏差门禁，见第 9 章） |
| ④ 池内覆盖 | < 60% | raise "qlib数据异常" |
| ⑤ NaN 比例 | > 5% | raise "特征NaN比例过高" |
| ⑤ 样本量 | train<10000 或 valid<1000 | raise "样本量异常" |
| ⑥ best_iter | == 0 | raise "模型退化为常数输出" |
| ⑥ best_iter | < 30 | 告警 + 自动 fallback 重训 |
| ⑥ valid RankIC | < 0.01 | 告警"预测力弱" |

**`best_iter` 是训练是否成功的第一判据。** 我实测跑 qlib 原生 LightGBM，日志是这样：

```
Training until validation scores don't improve for 50 rounds
[20]    train's l2: 0.928129    valid's l2: 1.00755
[40]    train's l2: 0.893824    valid's l2: 1.01606
Early stopping, best iteration is:
[1]     train's l2: 0.989025    valid's l2: 0.996795     ← best_iter = 1 !!
```

**只用了 1 棵树，172 个特征里只有 47 个被用到。** 这就是 RMSE 早停失效的现场：`valid's l2` 从第 1 轮起就在变大，早停立刻收工。

这解释了一个长期困惑：为什么 qlib 原生 LightGBM 在 Phase B 只有 18.19%（剔2020），而自研 RankIC 早停版的 LGB 有 18.55%、XGB 有 20.54%。**不是模型不行，是它们的早停指标错了。**

> 📌 **优化机会（优先级很高）**：`run_benchmark.py` 走的是 qlib 原生训练器，所以全部 14 个模型都在 RMSE 早停下被评估。如果给基准也接上 RankIC 早停，整个 Phase A/B 排名可能大幅重排。这是目前性价比最高的待办项。

## 4.2 重点模型 ① DoubleEnsemble（上线主力）

**为什么选它上线**：4 个批次结果稳定、Sharpe 稳定在 1.05–1.20、可复现性经过双跑验证（deC 与 deD 完全一致），且训练只需 ~14 分钟。**稳定和可复现比最高收益重要。**

### 它是怎么工作的

DoubleEnsemble 的核心是"**两个维度的重采样**"，底层是 3 个 LightGBM 子模型：

```
第 1 轮：用全部样本、全部特征训一个 LightGBM
   ↓ 算出每个样本的"学习难度"和每个特征的"重要度"
第 2 轮：SR（Sample Reweight）—— 给难学的样本加权重
        FS（Feature Selection）—— 只挑一部分特征
        用重新加权/筛选后的数据再训一个
   ↓
第 3 轮：同上，再训一个
   ↓
预测 = 3 个子模型加权平均（sub_weights = [1,1,1]，即等权）
```

**通俗理解**：像三个学生轮流考试。第一个考完，老师发现"这几道题大家都错"，就让第二个学生重点练这几道题，同时只给他一部分教材（防止死记硬背）。三个学生的答案投票决定最终结果。

### 超参逐个解释（`core/config.py` 第 105–119 行）

| 参数 | 值 | 含义 | 调它会怎样 |
|------|-----|------|-----------|
| `base_model` | `gbm` | 底层用 LightGBM | 唯一选项 |
| `num_models` | 3 | 3 个子模型 | 调到 5 更稳但慢 1.7 倍 |
| `enable_sr` | True | 开启样本重加权 | 关掉 = 退化成普通 bagging |
| `enable_fs` | True | 开启特征筛选 | 关掉 = 三个子模型看到同样特征，多样性下降 |
| `sample_ratios` | `[0.8,0.7,0.6,0.5,0.4]` | 按重要度分 5 档，各档特征的保留比例 | 数字越小筛得越狠 |
| `bins_sr` / `bins_fs` | 10 / 5 | 样本难度分 10 档 / 特征重要度分 5 档 | 一般不动 |
| `decay` | 0.5 | 历史轮次权重衰减 | 越小越"只看最近一轮" |
| `epochs` | 28 | 每个子模型的 boosting 轮数 | **固定 28 轮，不早停**（见下方警告） |
| `learning_rate` | 0.2 | 学习率 | 0.2 偏大，配 28 轮刚好 |
| `max_depth` / `num_leaves` | 8 / 210 | 树的复杂度 | 深树 + 重正则的组合 |
| `lambda_l1` / `lambda_l2` | 205.7 / 580.98 | L1/L2 正则（**非常重**） | 用来压制深树的过拟合 |
| `seed` | 43 | 随机种子 | 固定 |
| `deterministic` | True | LightGBM 确定性模式 | **别关**，否则不可复现 |
| `num_threads` | 6 | 线程数 | ⚠️ **别改**：线程数变动会改变结果 |

> ⚠️ **两个必须知道的坑**：
> 1. `epochs=28` 是**固定轮数、不做早停**，所以它天然躲过了 RMSE 早停失效的问题 —— 这也可能是它比原生 LightGBM 强那么多的真正原因（不是架构更好，是没被早停坑）。
> 2. `num_threads` 和 `deterministic` 影响复现性。`core/models.py` 的注释写得很明确："线程数变动也会影响结果，num_threads 已写死，不要随意改"。
> 3. DoubleEnsemble 的特征采样用**裸 `np.random`**，不重置全局随机流的话每次重训结果都不同。这就是 `train_qlib_model(seed_key=...)` 存在的原因，也是为什么 `run_benchmark.py` 要在文件头 `PYTHONHASHSEED=0` 重启自己。

### 怎么调它

```python
# core/config.py，"DoubleEnsemble" 的 kwargs
"num_models": 5,              # 更多子模型 → 更稳，代价是时间 ×1.7
"epochs": 50,                 # 更多轮数 → 拟合更充分，注意过拟合
"sample_ratios": [0.9, 0.8, 0.7, 0.6, 0.5],   # 筛特征更宽松
```

改完必须 `rm outputs/_phaseB_ckpt_*.pkl` 再重跑 Phase B，并且用新 `--tag`。

## 4.3 重点模型 ② GATs

**结论先说：这是当前最强的实测结果，也是最需要打折看的结果。**

Phase B 七窗口滚动（`outputs/benchmark_phaseB_gats.csv`）：

```
年化(全期) 48.91%    年化(剔2020) 47.00%    Sharpe 1.734
最大回撤 -29.44%     Calmar 1.661           RankIC 0.1291    换手 56.9%
```

Phase A 单切分时它就异常突出（RankIC 0.1841，第二名 0.0965），当时 README 的判断是"高度存疑，需 Phase B 多窗口验证"。**现在 Phase B 跑完了，7 个窗口滚动之后它依然遥遥领先**。README 第 156–167 行和 `docs/策略演进史` 番外章节里"待验证"的措辞已经过期，需要更新。

### 它是怎么工作的

GATs = **G**raph **AT**tention Network**s**（图注意力网络）。

```
① 每只股票的过去 20 天 × 172 个特征 → 喂进一个 LSTM → 压缩成一个 64 维的"股票状态向量"
② 把当天所有股票的状态向量放在一起，用注意力机制两两算"相似度"
③ 每只股票的最终表示 = 自己的向量 + 加权吸收其它相似股票的向量
④ 输出一个分数
```

**通俗理解**：树模型看每只股票是"孤立地看它自己的指标"。GATs 会问"**今天还有哪些股票跟我长得像？它们什么情况？**"，然后把同类股票的信息互相传递一遍再做判断。这在 A 股很合理 —— A 股是强板块联动市场，同一天同一板块的股票会一起动。

### 超参（`core/config.py` 第 146–151 行）

| 参数 | 值 | 说明 |
|------|-----|------|
| `d_feat` | 运行时注入 = 172 | 特征维度，由 `train_qlib_model` 自动改成实际列数 |
| `base_model` | `LSTM` | 先用 LSTM 抽时序特征 |
| `hidden_size` / `num_layers` | 64 / 2 | 隐层宽度 / LSTM 层数 |
| `dropout` | **0.7** | **极高**（其它模型 0.0~0.5），防止小样本过拟合的关键 |
| `lr` | 1e-4 | 学习率，比 LSTM 的 1e-3 小 10 倍（图模型不稳，要慢学） |
| `n_epochs` / `early_stop` | 200 / 10 | 最多 200 轮，10 轮不改善就停 |
| `metric` / `loss` | `loss` / `mse` | ⚠️ **走的是 MSE 早停**，同样存在指标错配风险 |
| `GPU` | -1 | 本机无 CUDA，强制 CPU |
| `model_path` | **已删除** | 官方 yaml 要求一个预训练 LSTM 权重文件，本机没有，改成从头训练 |

### 为什么还要打折看（4 个待排查项）

| 疑点 | 怎么验证 |
|------|---------|
| ① 结果是**修穿越 bug 之前**跑的（Phase B 日志显示 7 个窗口都用的旧分段 `valid 到 11-30`） | 用修好的 `build_windows()` 重跑，这是第一优先 |
| ② 存活偏差：只有 358 只股票有 2020-09-25 之后行情，而 GATs 靠"股票之间的关系"打分，池子被裁剪对它影响可能远大于树模型 | 补全行情后重跑对比 |
| ③ 注意力机制在小池子（137~303 只）上可能过拟合 | 打乱标签探针：`RUN_SLOW=1` 跑 `test_shuffle_label_collapses_rankic` |
| ④ 换手只有 56.9%，明显低于树模型的 82%，说明它选出的组合更"黏"。这可能是优点（真找到稳定信号），也可能是它在拟合某种缓变的东西（比如市值） | 做市值/行业中性化检验 |

> 📌 **在完成 ①②③④ 之前，不要把 GATs 上线，也不要把 48.91% 写进任何汇报。** 但它值得投入最多的排查时间 —— 如果这个数字在修完 bug 之后还能站住一半，就是这套系统迄今最大的发现。

## 4.4 重点模型 ③ 自研 RankIC 早停 XGB / LGB / ENS

这三个不在 `MODEL_CONFIGS` 里，只在 `run_rolling.py` 用，超参写在 `core/config.py` 第 39–52 行。

### XGB（`XGB_PARAMS`）

```python
"objective": "reg:squarederror",   # 回归目标
"learning_rate": 0.005,            # 极慢的火（配 1000 棵树上限）
"max_depth": 4,                    # 树只有 4 层 —— 很浅，刻意的
"colsample_bytree": 0.8879,        # 每棵树随机用 88.79% 的特征
"subsample": 0.8789,               # 每棵树随机用 87.89% 的样本
"reg_alpha": 10.0, "reg_lambda": 50.0,   # L1 / L2 正则
"disable_default_eval_metric": 1,  # 关掉默认 RMSE，换成自定义 RankIC
```

**设计思路**：金融数据信噪比极低，所以用"**很浅的树 + 很慢的学习率 + 很重的正则 + 每棵树只看部分数据**"这套组合，让模型只能学到最粗的规律，学不动噪声。

### LGB（`LGB_PARAMS`）

```python
"learning_rate": 0.02,             # 比 XGB 快 4 倍
"max_depth": 8, "num_leaves": 128, # 但树深一倍
"lambda_l1": 50.0, "lambda_l2": 200.0,   # 正则也重 4 倍来对冲
"metric": "None",                  # 关掉内置指标，走 RankIC feval
```

**为什么两个模型故意用不同风格**：XGB 是"浅树慢学"、LGB 是"深树重正则"。两个视角不同的模型，犯的错也不同，平均一下能互相抵消一部分噪声。像同一道菜请两位风格不同的厨子，各做一份再合议。

### ENS 集成

```
XGB 的预测 → 当天池内排名 → 百分位（0~1）
LGB 的预测 → 当天池内排名 → 百分位（0~1）
ENS 分数   = 两者平均
```

用**排名百分位**而不是原始预测值相加，因为两个模型输出的数值范围不一样，直接相加会让范围大的那个说话更响。

**效果验证**（`outputs/rolling10y_summary.csv`）：ENS 24.88% 明显高于 XGB 20.54% 和 LGB 18.55%，而且回撤（-33.95%）比 XGB 单独（-42.93%）小了 9 个百分点。**集成同时提高了收益和降低了回撤，这是真实的免费午餐。**

## 4.5 重点模型 ④ value_comp（不用机器学习的对照）

这是全系统最重要的**基准线**，因为它是"不用 ML 也能做到的水平"。

`core/valuation.py` 的 `value_comp_score`：

```
① 取 4 个估值倒数指标：
   EP  = 净利润 / 市值        （市盈率的倒数）
   BP  = 净资产 / 市值        （市净率的倒数）
   CFP = 现金流 / 市值        （市现率的倒数）
   SP  = 营业收入 / 市值      （市销率的倒数）
② 每个指标在当天池内算排名百分位（0~1，越便宜越接近 1）
③ value_comp = 4 个百分位的平均
④ 买 value_comp 最高的 20 只，等权
```

就是"**在一堆十年双正的好公司里，买最便宜的 20 只**"。没有训练、没有特征工程、没有超参。

**它的成绩**：剔2020 年化 23.11%、Sharpe 1.008、回撤 -19.34%、Calmar 1.068、换手 16.5%。

> 🎯 **这是你所有优化工作的及格线**。ML 模型如果只是年化更高但回撤和换手翻倍，Calmar 反而更差（DoubleEnsemble 0.917 < value_comp 1.068），那么从"风险调整后收益"角度看它并没有赢。**每次汇报都必须带上这一行做对比。**

`online_value/` 目录下的 `value_comp_M20` 是这个策略的实盘版本，有独立的冻结基准（`online_value/golden/backtest_baseline.csv`：年化 25.75%、Sharpe 1.26、OOS 29.28%）。注意那是**不同口径**（Top20、不同时间段、不同费率），不要和这里的 23.11% 混着比。

### qlib 表达式语法速查

| 写法 | 含义 | 注意 |
|------|------|------|
| `$close` `$open` `$high` `$low` `$volume` `$factor` | 原始字段 | `$factor` 是复权因子，真实价 = `$close/$factor` |
| `Ref($close, N)` | N 天**之前**的值 | **N 必须 > 0**，负数 = 穿越 |
| `Mean($close, 20)` | 20 日均值 | |
| `Std($close, 20)` | 20 日标准差 | |
| `Max/Min($close, 20)` | 20 日最大/最小 | |
| `Sum($volume, 20)` | 20 日累加 | |
| `Corr($close, Log($volume+1), 20)` | 20 日滚动相关系数 | 价量配合类因子常用 |
| `Rank($close, 20)` | 当前值在过去 20 天里的分位 | 时间序列分位，不是截面 |
| `Quantile($close, 20, 0.8)` | 20 日 80% 分位 | |
| `Slope/Rsquare/Resi($close, 20)` | 20 日线性回归的斜率/R²/残差 | |
| `Delta($close, 20)` | 当前 − 20 天前 | 等价 `$close - Ref($close,20)` |
| `If(cond, a, b)` | 条件选择 | |

**三条铁律：**
1. **分母永远加 `+1e-12`**：`Mean($volume,120)/($volume+1e-12)`。A 股停牌日 volume=0，不加就是除零 → inf → NaN 蔓延。
2. **别用负 Ref**。想不出别的穿越方式的话，这是最常见的一种。
3. **窗口不要超过 240 天**：窗口越长，每只股票需要的历史越长，新股会大量变 NaN，而 `NaN > 5%` 会直接 `raise`。

## 5.3 加一个基本面特征（PIT 规则严格得多）

基本面特征在 `core/features.py` 的 `load_fund_features()`，规则比量价严格：

## 5.4 改标签（改变预测目标）

```python
# core/dataset.py:19
DEFAULT_LABEL = ["Ref($close, -20) / $close - 1"]     # 未来 20 天涨幅
```

想改成"未来 10 天"（更高频）：

```python
DEFAULT_LABEL = ["Ref($close, -10) / $close - 1"]
```

**但必须同时改 `core/config.py`：**

```python
LABEL_HORIZON = 10      # 原来 20，必须和标签里的数字一致
```

**为什么必须同步改？** `LABEL_HORIZON` 有三个用途：
1. `assert_purged()` 用它验证 purge gap 够不够（改小了 gap 可以缩短，改大了 gap 必须加长）
2. `forward_return_matrix()` 用它算 OOS IC 时对齐的前瞻收益
3. `_config_hash()` 把它哈希进去 → 所有冻结模型立刻失效，强制重训

**改了之后必须重新检查 purge**：如果你把 horizon 从 20 改成 40，现有的"一个月留白"就不够了（40 个交易日 ≈ 两个月），`assert_purged` 会 raise 并明确告诉你侵入了几个交易日。这时候要去 `build_windows()` 把 gap 加长。

> 📌 **标签是唯一允许出现"负 Ref"的地方** —— 因为标签本来就是未来收益。但它绝不能进入 `feature` 组。守卫测试 `test_no_feature_equals_future_label` 专门检查有没有哪列特征跟未来收益近乎完全相关（那就是标签漏进特征了）。

## 5.6 特征工程红线（会造成穿越的 5 种写法）

| ❌ 错误写法 | 为什么错 | ✅ 正确做法 |
|-----------|---------|-----------|
| `Ref($close, -5)` 放进 feature | 用了 5 天后的价格 | 只用正 Ref |
| 用全期 mean/std 标准化特征 | 未来的分布信息泄露到过去 | 用 `RobustZScoreNorm(fit_start=train.start, fit_end=train.end)`，已在 `_handler_config` 里配好 |
| 用今天的股票名单回溯历史池子 | 存活偏差（退市/停牌的股票被悄悄剔除） | `build_dynamic_universe(Y)` 的 year-2 规则 + `assert_market_coverage` 门禁 |
| 财务因子用披露年直接生效 | 年报 4 月底才出，1 月用就是穿越 | `Y+1-05-01` 生效 |
| 用 `$close` 算成交额判断流动性 | `$close` 是后复权价，不是真实成交价 | 真实价 = `$close / $factor`（`tools/fetch_ohlcv.py` 的口径） |

# 第 6 章 看特征重要性

> 代码库里原本**没有**特征重要性功能，`tools/feat_importance.py` 是为此新增的，两种模式都已实测跑通。

## 6.1 两种口径，回答的是完全不同的问题

| | `--mode gain`（原生增益） | `--mode perm`（置换重要性） |
|---|---|---|
| **它在问什么** | 训练时这一列被用来分裂了多少次、贡献多少增益 | 把这一列打乱后，**样本外预测力**掉多少 |
| **在哪段数据上算** | **train 段**（拟合过程中的统计） | **valid 段**（模型没见过的排序表现） |
| **支持的模型** | 只有树模型 + Linear | **全部**（DL 模型只能用这个） |
| **速度** | 训练完立刻出（秒级） | 每列一次预测（172 列要几十分钟） |
| **能用来删特征吗** | **不能** | **能，这是唯一合理判据** |

**为什么 gain 不能用来删特征**：gain 衡量的是"模型有多爱用它"，但噪声列在训练集上也能刷出很高的 gain（因为它恰好能把训练样本切得很整齐）。**模型爱用 ≠ 对未来有用。**

我实测的结果就是活生生的证明（下一节）。

## 6.2 用法与实测结果

### 命令

```bash
cd /Users/11164591/Documents/Qoder目录/qlib/quant

# ① 原生增益（最快，1 分钟内出结果，先跑这个建立直觉）
PYTHONPATH=. /usr/bin/python3 tools/feat_importance.py --model LightGBM --year 2026 --topn 25

# ② 重点模型
PYTHONPATH=. /usr/bin/python3 tools/feat_importance.py --model DoubleEnsemble --year 2026 --topn 20

# ③ 置换重要性：只测 gain 前 40 列（推荐，全 172 列太慢）
PYTHONPATH=. /usr/bin/python3 tools/feat_importance.py --model LightGBM --year 2026 \
    --mode perm --perm-topn 40 --n-repeat 3

# ④ 两种一起跑
PYTHONPATH=. /usr/bin/python3 tools/feat_importance.py --model DoubleEnsemble --year 2026 \
    --mode both --perm-topn 30

# ⑤ DL 模型只能走 perm（很慢，先小范围试）
PYTHONPATH=. /usr/bin/python3 tools/feat_importance.py --model GATs --year 2026 \
    --mode perm --perm-topn 15
```

| 参数 | 默认 | 说明 |
|------|------|------|
| `--model` | LightGBM | `MODEL_CONFIGS` 里任意模型名 |
| `--year` | 2026 | 用哪个滚动窗口（W2020~W2026） |
| `--mode` | gain | `gain` / `perm` / `both` |
| `--topn` | 40 | 终端展示前 N 行 |
| `--perm-topn` | 0 | perm 只测 gain 前 N 列；0 = 全部（很慢） |
| `--n-repeat` | 1 | 每列重复打乱几次取均值，**建议 ≥3** 降噪 |
| `--seed` | 42 | 打乱的随机种子，固定以便复现 |

产出：`outputs/featimp_{模型}_W{年}_{gain|perm}.csv`（tab 分隔）。

**无穿越保证**：训练只用 train 段，置换评估只用 valid 段，**一次都不读 test 段**。所以你可以放心用它的结论指导特征取舍，不会污染样本外评价。（对 pytorch 序列模型有个技术细节：它们的 `predict()` 没有 `segment` 参数，工具会把 dataset 的 test 段**指向 valid 区间**，本质上还是在 valid 上评估。）

### 实测结果 ①：三个模型都在看什么（W2026，gain）

| 1 | **STD120** | 23.28% | MA120 | 2.05% | **STD240** | 7.74% |

| 3 | **STD240** | 10.97% | SUMD30 | 1.92% | CORD60 | 5.70% |
| 4 | ROC30 | 5.10% | RANK30 | 1.39% | **ROC120** | 5.10% |
| 5 | MA240 | 4.68% | VSTD10 | 1.31% | WVMA60 | 4.20% |
| 6 | WVMA60 | 3.68% | **VMA240** | 1.30% | **VMA240** | 4.17% |

| — | 用到的列数 | **47/172** | 用到的列数 | **161/172** | 用到的列数 | **156/172** |

**三个重要发现：**

1. **`Alpha158Enhanced` 自己加的 14 个长周期因子确实在起作用**：`STD120`、`STD240`、`MA120`、`MA240`、`ROC120`、`VMA240`、`CORR_PV60` 全部进了 top10。加这 14 个因子是有效的改动。
2. **长周期波动率（STD120/STD240）是三个模型共同的最重要特征**。这意味着模型很大程度上在做"**低波动因子**"——买波动小的股票。这是学术上公认的有效因子，但也提醒你：模型的超额可能主要来自暴露在低波动风格上，不是什么神秘的 alpha。
3. **LightGBM 只用了 47/172 列，且 STD120 一个人占 23%** —— 因为它 `best_iter=1`（只有一棵树，RMSE 早停失效）。XGBoost 用了 161 列、DoubleEnsemble 156 列，分布均匀得多。**看"用到的列数"就能一眼判断模型有没有被早停坑。**

### 实测结果 ②：gain 高 ≠ 有用（W2026，LightGBM，perm）

基线 valid RankIC = **0.0387**。把每列打乱后重新评估：

| gain 排名 | 特征 | gain 占比 | 打乱后 RankIC | **RankIC 下降** | 结论 |
|---|------|---------|-------------|--------------|------|
| 2 | **QTLD60** | 13.66% | 0.0168 | **+0.0219** | ✅ 真的重要 |
| 4 | ROC30 | 5.10% | 0.0315 | +0.0072 | ✅ 有用 |
| 7 | MA60 | 3.60% | 0.0328 | +0.0059 | ✅ 有用 |
| **1** | **STD120** | **23.28%** | 0.0335 | **+0.0052** | ⚠️ **gain 第一，实际贡献只排第四** |
| 5 | MA240 | 4.68% | 0.0380 | +0.0007 | ⚠️ 几乎没贡献 |
| 6 | WVMA60 | 3.68% | 0.0398 | **−0.0011** | ❌ 删了更好 |
| 8 | CNTN60 | 3.26% | 0.0415 | **−0.0028** | ❌ 删了更好 |
| **3** | **STD240** | **10.97%** | **0.0695** | **−0.0307** | ❌❌ **删了 RankIC 涨 80%！** |

**这就是全文最重要的一张表。** `STD240` 的 gain 排第 3（占 10.97%），但把它打乱之后，valid RankIC 从 0.0387 **涨到 0.0695** —— 它不是没用，**它在害模型**。

> 🎯 **教训：绝对不要用 gain 排名来决定删哪个特征。** gain 只告诉你"模型在关注什么"，perm 才告诉你"这个关注有没有价值"。
>
> （注：这个 perm 实测是在 `best_iter=1` 的退化模型上做的，本身有噪声。所以用 perm 做决策时**一定要 `--n-repeat 3` 以上**，并且在一个收敛正常的模型上做。）

## 6.3 从重要性到删特征的完整流程

```
① 跑 gain，看模型在关注什么，用到了几列 / 172
      ↓ 如果"用到的列数"很少（<60），先去修早停问题，别急着动特征
② 跑 perm --perm-topn 40 --n-repeat 3（在收敛正常的模型上）
      ↓
③ 挑出 ic_drop ≤ 0 的列 —— 工具会直接打印
      "[!] N/M 列打乱后 RankIC 不降反升 → 这些列大概率是噪声"
      ↓
④ 换 2~3 个窗口（--year 2024 / 2025 / 2026）重复步骤 ②③
      ↓ 只保留"**在多个窗口里都是负贡献**"的列 —— 单窗口结论不可信
      ↓
⑤ 从 core/features.py 删掉这些列（如果是 Alpha158 自带的列，
   需要在 get_feature_config 里过滤掉，而不是改 qlib 源码）
      ↓
⑥ 完整走 5.5 的检查清单 → Phase A → Phase B（新 tag）
      ↓
⑦ 只有 Phase B 多窗口的 RankIC / Calmar 都改善才算数
```

想过滤掉 Alpha158 自带的某些列，正确做法是在自己的 handler 里筛：

```python
class Alpha158Enhanced(Alpha158):
    DROP = {"STD240", "WVMA60", "CNTN60"}          # 经多窗口 perm 验证的负贡献列

    def get_feature_config(self):
        fields, names = super().get_feature_config()
        extra_fields = [...]      # 原有扩展
        extra_names = [...]
        f_all, n_all = fields + extra_fields, names + extra_names
        keep = [(f, n) for f, n in zip(f_all, n_all) if n not in self.DROP]
        return [f for f, _ in keep], [n for _, n in keep]
```

## 6.4 特征重要性的 4 个陷阱

| 陷阱 | 说明 |
|------|------|
| **共线性稀释** | 172 列里有一堆高度相关的（STD20/STD60/STD120/STD240）。打乱其中一个，模型能从另外三个补回信息 → 四个的 perm 值都很低，看起来"都不重要"，但整组删掉就崩了。**遇到明显同族的因子要整组一起测。** |
| **单窗口噪声** | 一个窗口的 perm 结果波动很大（本节实测就是例子）。**必须多窗口 + `--n-repeat ≥3`。** |
| **退化模型的重要性没意义** | `best_iter=1` 时模型只有一棵树，重要性完全是噪声。工具会在基线 RankIC ≈ 0 时直接 `raise`，但 0.0387 这种"很低但非零"的情况它不会拦，需要你自己判断。 |
| **gain 的 importance_type** | 工具统一用 `importance_type="gain"`（总增益）。qlib 官方 `get_feature_importance` 默认是 `split`（分裂次数），两者排名可以差很远。用 split 会让"取值多的连续特征"天然占优。 |

> 🔧 **一个已修的实现细节**（如果你要读工具代码）：qlib 的 `DEnsembleModel.get_feature_importance()` 官方实现有 bug —— 它用 `_model.feature_name()` 拿到的是 `Column_k`，而 `k` 是**子特征集内**的位置，不同子模型的 `Column_0` 指向不同的真实列，直接相加会串味。`tools/feat_importance.py` 改用 `model.sub_features` 逐子模型还原真名后再累加。同理，XGBoost/LightGBM 的 wrapper 训练时传的是 `x.values`，列名在 booster 里丢失成 `f0`/`Column_0`，工具统一按**位置**映射回真实列名。

# 第 7 章 关注效果：指标与产出文件

## 7.1 九个指标：每个是什么、看到多少算好

所有指标都在 `core/backtest.py` 的 `calc_metrics()` 里算，**一年按 244 个交易日**。

| # | 指标 | 代码 | 一句话解释 | 怎么看 |
|---|------|------|-----------|--------|
| 1 | **年化收益** | `ar` | 整段回测的复合年增长率。`(1+r).prod()**(1/年数)-1` | 全期（2020-01 起） |
| 2 | **年化(剔2020)** | `annualized_since` | **只从 2021-01-01 起**算年化 | ⭐ **看这个** |
| 3 | 年化波动 | `vol` | 日收益标准差 × √244 | 25–35% 是 A 股小盘常态 |
| 4 | **Sharpe** | `sharpe = ar/vol` | 每承担 1 单位波动换来多少收益 | > 1.0 合格，> 1.5 优秀 |
| 5 | **最大回撤** | `mdd` | 从历史最高点跌下来的最大幅度 | ⭐ 你能不能扛住 |
| 6 | **Calmar** | `calmar = ar / abs(mdd)` | 每承担 1 单位回撤换来多少收益 | ⭐ **最该看的综合分**，> 1.0 好 |
| 7 | IC | 相关系数 | 打分与实际涨幅的皮尔逊相关 | 0.05 就算有效 |
| 8 | **RankIC** | 秩相关 | 打分排名与实际涨幅排名的相关 | ⭐ 0.05 有效，0.08 强，0.13 很强 |
| 9 | 换手率 | `turnover` | 每月单边换掉多少仓位 | 越低越好（省摩擦） |

### 为什么"剔2020"这么重要

`annualized_since(returns, "2021-01-01")` 这个口径存在的原因是：**2020 年是极端牛市**（A 股 2020 年结构性大涨），把它算进去所有模型的年化都会虚高一大截。

看差距有多大（Phase B 实测）：

| 模型 | 全期年化 | 剔2020年化 | 差距 |
|------|---------|-----------|------|
| GATs | 48.91% | 47.00% | −1.9pp |
| DoubleEnsemble(tree批) | 31.77% | 27.60% | **−4.2pp** |
| LSTM | 17.53% | 12.03% | **−5.5pp** |
| MLP | 10.92% | 4.58% | **−6.3pp** |
| value_comp Top20 | 20.66% | **23.11%** | **+2.5pp**（唯一变好的） |

`value_comp` 剔掉 2020 反而变好 —— 说明它的收益不是靠 2020 那波，而是持续赚的。**这是个很强的信号。** MLP 剔掉 2020 只剩 4.58%，说明它基本上只是在 2020 年蹭了一波大盘。

> 🎯 **对比模型时永远看"剔2020"那一列。** 全期数字只用来对外汇报。

### 为什么 Calmar 比 Sharpe 更该看

Sharpe 用的是波动率，波动率把"涨得猛"和"跌得狠"同等对待。但你真正扛不住的是回撤。

| 模型 | 剔2020年化 | Sharpe | 回撤 | Calmar |
|------|-----------|--------|------|--------|
| DoubleEnsemble(deC) | 26.48% | 1.092 | −40.40% | 0.700 |
| value_comp Top20 | 23.11% | 1.008 | **−19.34%** | **1.068** |

两者年化差 3.4pp、Sharpe 几乎一样，但 DE 要你扛 40% 的回撤，value_comp 只要 19%。**从 Calmar 看，value_comp 才是更好的策略**（1.068 vs 0.700）。这就是为什么上线方案里 value_comp 占 60% 而 DE 只占 40%。

### IC 和 RankIC 的区别与陷阱

- **IC**：打分与真实涨幅的线性相关。会被极端值主导（一只翻倍股能把整个月的 IC 拉起来）。
- **RankIC**：只看排名。更稳健，也更贴合"我只买 Top10"这个用法。

⚠️ **RankIC 高不一定收益高**：看"十年双正池等权"这一行 —— RankIC 0.0914 是全表**第二高**（仅次于 GATs），但年化只有 5.19%。因为它是等权买全部几百只，RankIC 再高也没转化成 Top10 的超额。**RankIC 衡量的是"全池排序能力"，年化衡量的是"头部选股能力"，两者不是一回事。**

必看三项：

# 第 8 章 持续优化的标准工作流

这一章是你以后的**日常主战场**。

## 8.1 三条铁律

### 铁律一：先证伪，再相信

任何一个改动，你的默认假设应该是"**它没用**"，然后去尝试推翻这个假设。而不是反过来（默认它有用，然后找证据支持）。

具体做法：一个改动必须在 **Phase B 的 7 个滚动窗口上都跑一遍**，只有多窗口一致改善才算数。单窗口改善大概率是噪声。

**反例（真实踩过的坑）**：`STD240` 这个特征在 W2026 的 gain 排第 3，看起来很重要 —— 实际 perm 一测，删了 RankIC 涨 80%。如果只看 gain 就下结论，会保留一个害模型的特征。

### 铁律二：一次只改一件事

改了特征又改了超参，结果变好了 —— 你不知道是哪个起的作用，也不知道另一个是不是在拖后腿。以后要撤销都不知道撤哪个。

### 铁律三：valid 用来选，test 只用来一次性验收

- `valid` 段：调超参、选特征、早停 —— 可以反复看，随便看。
- `test` 段：**每个改动只允许看一次**。

如果你反复看 test 结果来调参，test 就变成了第二个 valid，你的"样本外"就名存实亡了。这叫**多重比较偏差**，是量化研究里最隐蔽的自欺欺人。

> 实操建议：在本地开一个 `docs/optim_log.md`，每次改动**先写下预期**，再跑 test。这样你自己能看出哪些改动是"事后编故事"。

## 8.2 七步优化循环

```
① 提出假设
   "我觉得 XXX 会改善，因为 YYY"（必须能说出机制，不能只是"试试看"）
        ↓
② 用最便宜的方式验证
   feat_importance（1 分钟）→ 单窗口训练 → Phase A（数小时）→ Phase B（数小时）
   能在 1 分钟内否掉的，就别花 4 小时
        ↓
③ 改代码，一次只改一处
   记下改了什么（git commit 或写进 optim_log.md）
        ↓
④ 跑守卫单测
   PYTHONPATH=. /usr/bin/python3 -m pytest tests/test_no_lookahead.py -q
   （改了 dataset/universe/features 必跑，防止引入穿越）
        ↓
⑤ 跑 Phase B，用新 tag
   --tag 你的实验名   ← 绝不覆盖旧结果，方便回头对比
        ↓
⑥ 对比：新 tag vs 旧 tag，看剔2020年化 / RankIC / Calmar / 回撤 四项
        ↓
⑦ 判决
   四项里 ≥3 项改善且无一项显著恶化 → 采纳，更新 FROZEN 基准
   否则 → 撤销，把结论写进 optim_log.md（**负面结论也是资产**，防止半年后再踩）
```

## 8.3 优化优先级：从性价比最高的开始

按"预期收益 / 投入成本"排序，**从上往下做**：

| 优先级 | 事项 | 为什么值得 | 预估工作量 |
|--------|------|-----------|-----------|
| 🔴 **P0** | **重跑全部结果**（第 9 章两个坑修复后） | 不做这个，下面所有对比都没有基准 | 1 天（挂机） |
| 🔴 **P0** | **给 qlib 原生模型接上 RankIC 早停** | 实测 LightGBM `best_iter=1`、只用 47/172 列；XGBoost valid-rmse 单调上升。**14 个模型的排名可能大幅重排** | 半天改 + 一天跑 |
| 🟠 **P1** | GATs 的 48.91% 是不是真的 | 它比第二名高 17pp，太反常，必须排查（见 4.3） | 半天 |
| 🟠 **P1** | 排查种子集成为什么变差 | deENS 21.98% < deC 26.48%，违反直觉 | 半天 |
| 🟡 **P2** | 用多窗口 perm 删掉负贡献特征 | 172 列里肯定有噪声列 | 1 天 |
| 🟡 **P2** | 降低换手率（82%/月太高） | 摩擦已扣但滑点没扣，实盘会比回测差 | 1 天 |
| 🟢 **P3** | 调超参（learning_rate / num_leaves / …） | 边际收益最小，但最容易做 | 挂机 |
| 🟢 **P3** | 加新特征 | 收益不确定，且有过拟合风险 | 不限 |

> 🎯 **不要一上来就调超参和加特征。** 上面 P0 的两项对结果的影响，比你调一百组超参都大。`best_iter=1` 意味着模型只有一棵树 —— 在这个状态下调 `num_leaves` 是完全没有意义的。

## 8.4 为什么"RMSE 早停"是当前最大的问题

这是本手册想让你记住的**最重要的技术结论**。

qlib 原生的 `LGBModel` / `XGBModel` 用的早停指标是 **RMSE（预测误差）**。但标签经过 `CSZScoreNorm` 之后，均值 0、标准差 1，而股票收益的可预测部分极小 —— **在这种数据上，"什么都不预测、全部输出 0"的 RMSE 就已经接近最优了**。

于是发生了这个事（实测日志原文）：

```
[LightGBM] Early stopping, best iteration is: [1]
```

第 1 棵树之后 RMSE 就不再下降，早停立刻触发，模型只剩一棵树。XGBoost 那边更直白：

```
valid-rmse: 0.99840 → 0.99902 → 1.00104 → ... → 1.00619
```

**valid-rmse 从头到尾单调上升**，也就是说从第一棵树开始，模型在 RMSE 口径下就一直在"变差"。

但同一批数据，用 RankIC 当早停指标（`core/models.py` 自研训练器），`best_iter` 能跑到 **686**：

```
W2020  2020  XGB  pool=137  n_inst=129  best_iter=686  valid_rank_ic=0.0805
```

**为什么 RankIC 能行而 RMSE 不行**：我们根本不在乎预测值准不准（标签都被截面标准化了），只在乎**排序对不对**。RankIC 直接衡量排序，RMSE 衡量数值误差。用错了指标，早停就在错误的地方停下。

`core/models.py` 里为此做了三道保险：
1. 自定义 `RankICEval` 作为 early stopping 的 eval 指标
2. `N_ROUNDS=1000` / `EARLY_STOP=100`（给足耐心，不轻易停）
3. 训练完把 `best_iter` 和 `valid_rank_ic` 写进 `rolling10y_train_diag.csv`，让退化无处可藏

**这意味着**：Phase A/B 里全部 14 个 qlib 原生模型的成绩，都是在"早停失效"状态下取得的。给它们接上 RankIC 早停之后，排名可能大幅重排 —— **这是当前性价比最高的一件待办事项。**

改法思路（`core/models.py` 的 `train_qlib_model`）：给 LGBModel/XGBModel 传自定义 `eval_metric` / `feval`，或者干脆让它们走自研训练器那条路。改完必须重跑 Phase A + Phase B（新 tag）。

## 8.5 调参优先级（真要调超参的时候）

树模型（DoubleEnsemble / XGBoost / LightGBM）按影响力排序：

| 顺序 | 超参 | 怎么调 | 说明 |
|------|------|--------|------|
| 1 | `learning_rate` | 0.05 → 0.02 → 0.01 | 调小要同时调大 `num_boost_round` |
| 2 | `num_leaves` / `max_depth` | 减半试 | 主要的过拟合旋钮 |
| 3 | `feature_fraction` / `colsample_bytree` | 0.9 → 0.7 → 0.5 | 172 列有共线性，降采样通常有帮助 |
| 4 | `lambda_l1` / `lambda_l2` | ×10 试 | 正则 |
| 5 | `bagging_fraction` / `subsample` | 0.9 → 0.7 | 行采样 |

DL 模型（GATs / LSTM / GRU / ALSTM / …）：

| 顺序 | 超参 | 说明 |
|------|------|------|
| 1 | `lr` | 最敏感，1e-3 → 3e-4 → 1e-4 |
| 2 | `n_epochs` + `early_stop` | DL 早停也是 loss 口径，同样有 8.4 的问题 |
| 3 | `hidden_size` / `num_layers` | 数据量不大（几百只股票），别堆太大 |
| 4 | `dropout` | 0.0 → 0.3 |
| 5 | `batch_size` | TS 模型是按日 batch，改动影响梯度噪声 |

**调参不要用网格搜索。** 池子只有几百只股票、样本外只有 7 个窗口，网格搜索出来的"最优超参"几乎必然是过拟合到 valid 段的。一次调一个参数、看单调趋势就够了。

### `--checkpoint` / `--tag`：断点续跑与结果隔离

### `--seeds`：种子集成

```bash

```

`zscore_mean`（`core/pipeline.py`）先把每个种子的预测**按日截面 z-score 标准化**再平均。直接平均原始分数是错的 —— 不同种子的分数量纲不同，会被方差最大的那个主导。

⚠️ **但实测种子集成反而变差了**：

| 批次 | 配置 | 剔2020年化 | Sharpe | Calmar |
|------|------|-----------|--------|--------|
| deC/deD | 单种子 | **26.48%** | 1.092 | 0.700 |
| deENS | 3 种子集成 | **21.98%** | 0.931 | 0.675 |

**掉了 4.5pp**，这违反直觉（集成应该降噪）。可能的原因，按可能性排序：

1. **单种子那个 26.48% 本身就是运气好**，三种子平均才是真实水平 —— 如果是这样，那才是好事（说明我们发现了虚高）
2. `zscore_mean` 融合后的分数分布变了，Top10 的切分位置随之改变
3. DoubleEnsemble 内部本身已经是集成（多个子模型 + 样本重加权），再套一层外部集成产生了过度平滑

**怎么排查**：跑 5–7 个种子，看单种子成绩的**分布**。如果单种子成绩在 21%–27% 之间散布，那 26.48% 就是上尾运气，集成的 21.98% 反而更可信 —— **这个排查结果会直接改变你对整个策略收益水平的判断，所以值得优先做。**

### `--budget`：单模型时间上限

`BENCH_MODEL_BUDGET_SEC = 2700`（45 分钟）。超时的模型会被跳过并在日志标注，防止一个 DL 模型卡死整个批次。

## 9.1 坑一：valid → test 的标签穿越（代码已修，结果未重跑）

### 问题是什么

标签是 `Ref($close, -20) / $close - 1`，也就是说 **一个样本的标签需要用到它之后 20 个交易日的价格**。

旧的窗口切分（`core/universe.py`）是这样：

```
train:  (Y-5)-01-01  ~  (Y-2)-12-31      ← 末尾紧贴 valid 起点
valid:  (Y-1)-01-01  ~  (Y-1)-11-30      ← 末尾紧贴 test 起点
test:   (Y-1)-12-01  ~  ...
```

看着没毛病，三段不重叠。但加上标签的 20 天视野：

```
valid 最后一天 = (Y-1)-11-30
它的标签用的是 (Y-1)-11-30 之后 20 个交易日的价格 ≈ (Y-1)-12-28
                                                    ↑
                                        这已经在 test 段里面了！
```

**valid 末尾约 20 个交易日（约 9% 的 valid 样本）的标签，包含了 test 期的价格信息。** 而 early stopping 用的就是 valid RankIC 来决定"训练几轮停下"。

→ **模型选择过程间接偷看了测试集。这是真穿越。**

同理，train 末尾 20 个交易日的标签落在 valid 段内，让早停失去了独立性（这个相对轻微，属于方法论瑕疵）。

### 修复

`core/universe.py`（2026-07-31 21:27 改的）两段末尾各回撤一个月，留出 **purge gap**（学术上叫 purged cross-validation，见 López de Prado）：

```python
def build_windows():
    for y in range(2020, 2027):
        wins.append({
            "train": (f"{y-5}-01-01", f"{y-2}-11-30"),   # purge: 末尾留白至 valid.start
            "valid": (f"{y-1}-01-01", f"{y-1}-10-31"),   # purge: 末尾留白至 test.start
            "test":  (f"{y-1}-12-01", sig_end),
            "bt_end": bt_end})
```

同时新增了真检查 `assert_purged()`：**用真实交易日历**验证每段末尾样本的标签结束日必须早于下一段起点。

> 代码注释里有一句很值得读的话：
>
> > *"只比对日期字符串（如 `endswith("-11-30")`）形同虚设 —— 历史上正是这个假检查放过了 valid→test 的 20 日侵入。"*
>
> 教训：**守卫测试如果只检查表面形式，等于没有守卫。** 检查必须落到真实的业务含义上（这里是"标签的最后一个价格日"）。

另外，代码注释还明确纠正了一个流传已久的错误说法：

> > *"旧的『12月留白』说法是错的 —— 12月恰是 test 段第一个月，留白从未存在。"*

如果你在旧文档或 commit message 里看到"12月留白"，那是错的。

## 9.2 坑二：行情覆盖导致的存活/前视偏差（门禁已加，数据在重抓）

### 问题是什么

`core/data.py` 的注释记录了这个发现：

> *"cn_data 里 3943 只股票中只有 **358 只**有 2020-09-25 之后的行情，其余 3585 只全部截断在拼接点。而那 358 只恰好 ≈ 用最新财务数据算出的近年股票池（W2025/W2026 覆盖 100%，W2020 仅 54.7%）"*

翻译成人话：**行情数据本身就是用"今天才知道的名单"筛出来的。**

1. **前视选择偏差**：2020 年回测时，可交易的宇宙其实是"2026 年我们认为好的那 358 只"。这些公司之所以到 2026 年还在池子里，正是因为它们这十年一直赚钱 —— 你用未来的胜利者名单去跑历史。

## 10.1 上线纪律：年度训练 + 月度只推理

这是整个上线设计的核心一句话：

> **模型一年只训练一次，每个月只做推理，不训练。**

为什么？如果每个月都重训，那么持仓会随着"这个月新增的训练数据 + 随机种子 + 早停轮数"漂移。你会发现同一只股票这个月买、下个月卖、下下个月又买回来 —— **换手率暴涨，摩擦吃掉全部收益，而且你根本不知道是策略在动还是模型在抖。**

固定模型之后：同一个信号日重复运行，**结果完全一致**（`predict_frozen` 的复现性契约）。

## 10.2 三重凭证：确保"跑的是你以为的那个模型"

`core/pipeline.py` 的 `freeze()` 会写一个 manifest，包含三样东西：

| 凭证 | 防什么 | 校验时机 |
|------|--------|---------|
| **SHA256**（每个 pkl 一个） | 模型文件被替换、损坏、手工改过 | `load_frozen` 时逐文件校验，不匹配直接 `raise` |
| **config_hash** | 超参 / TOPK / 标签视野 / 费率 / 流动性阈值被改动 | `load_frozen` 时比对，不一致直接 `raise` |
| **git_commit** | 代码版本 | 只记录，不强制校验（供事后追溯） |

`load_frozen` 的两个报错长这样，看到就知道怎么办：

```
[CHECK] config 已变更 (冻结时 4a3e9640d387df49 → 现在 8b1c...)!
    超参或回测口径被改动, 冻结模型已失效 → 必须重新年度训练。

[CHECK] DoubleEnsemble_W2026_s0.pkl SHA256 不匹配, 模型文件已被修改!
```

> 关于 pickle 安全：模型文件**只由 `freeze()` 自产自用**，且 load 前强制校验 SHA256。**永远不要加载外部来源的 pkl** —— pickle 可以执行任意代码。

## 10.5 sleeve 分仓：为什么是 40/60、15 只

`core/portfolio.py`：

```python
SLEEVES = {
    "DE":  {"weight": 0.40, "topk": 5},    # 模型腿：每月轮动
    "V20": {"weight": 0.60, "topk": 10},   # 价值腿：value_comp，低换手
}
LOT = 100                # A股一手 = 100 股
LOT_SKIP_RATIO = 1.5     # 一手金额 > 目标仓位 × 1.5 → 买不起，顺延下一名
MIN_TICKET = 3000        # 单笔低于此金额，佣金占比过高（免5券商下 5/3000 = 0.17%）
```

**为什么不做信号融合、而是分仓？**

两条腿的资金**各自独立**，不把 DE 的分数和 value_comp 的分数融成一个综合分。原因：

1. 两个分数量纲、分布、有效周期完全不同，融合的权重是又一个要调的超参（又一个过拟合机会）
2. 分仓下你能清楚看到"这个月是哪条腿在赚钱"，融合了就看不出来
3. 重合的股票**自然加仓**（`merge_overlap` 把两笔合成一笔），相当于"两个独立体系都看好"的股票自动多买 —— 这比人为设计的融合权重更朴素可信

**为什么是 40/60？** value_comp 的 Calmar（1.068）远好于 DE（0.700），所以给它更大权重。README 记录的组合口径是：15 只持仓 / 换手 46.2%/月 / 剔2020年化 28.9%。

## 10.6 一手取整：小资金的硬约束

A 股一手 = 100 股。5 万资金买 15 只，每只目标 3000 元左右 —— 一只 60 元的股票，一手就是 6000 元，**买不起**。

`allocate()` 的处理逻辑（按顺序）：

```
对排序名单里每一只，从第 1 名开始：
  ① 没价格 → 跳过，理由"无价格"
  ② 一手金额 > 目标仓位 × 1.5 → 跳过，理由"一手 X 元 > 目标 Y × 1.5"
                                 （买它会严重破坏等权，顺延给下一名）
  ③ 手数 = 目标仓位 // 一手金额，至少 1 手
  ④ 再按"腿内钱包余额"收敛，买不起就顺延（绝不透支）
  ⑤ 填满 topk 只就停
最后：余钱补仓
  用剩余现金给"当前离目标最远"的持仓补一手，逼近等权
  但补完若超出目标 × 1.5 就不补（宁留现金，不破坏等权）
```

**为什么要"余钱补仓"这一步？** 因为手数向下取整会留下大量闲置现金（小资金下可达 10%+），而**回测是满仓口径** —— 现金拖累会直接吃掉收益。补仓后实测 `cash_pct` 能压到 0.5% 左右。

### 一个容易致命的细节：下单价必须用真实价，不是复权价

`latest_prices()`：

```python
real = px["$close"] / px["$factor"]
```

qlib 里的 `$close` 是**后复权价**，和你券商界面看到的价格不是一回事。代码注释里的实测数据：

> *"实测原 cn_data 中 358 只里有 **54 只**两者相差 10% 以上（最大 **1.89 倍**）—— 直接用 `$close` 会把『一手多少钱』算错到 ±90%，一手取整 / 买不起顺延的判断全部失效。"*

**所以：凡是涉及"多少钱"的计算（下单金额、一手判断、流动性阈值），都必须用 `$close / $factor`。** 只有涉及"涨了多少"的计算（收益、特征、标签）才用复权价 `$close`。

# 附录 C 名词表

| 名词 | 白话解释 |
|------|---------|
| **因子 / 特征** | 描述一只股票某个属性的数字，比如"过去 20 天涨幅""市盈率倒数"。模型的输入。 |
| **标签 / Label** | 我们希望模型预测的东西。这里是"未来 20 天涨幅（截面标准化后）"。 |
| **截面 / 横截面** | "同一天所有股票"这个维度。截面标准化 = 拿同一天大家的平均值和标准差做归一。 |
| **IC** | 打分与真实涨幅的相关系数。衡量预测能力。 |
| **RankIC** | 打分**排名**与真实涨幅**排名**的相关系数。比 IC 稳健，本系统的核心指标。 |
| **前视偏差 / Look-ahead** | 用了当时还不存在的信息。比如 1 月选股用了 4 月才披露的年报。 |
| **穿越** | 前视偏差的口语说法。 |
| **存活偏差 / Survivorship bias** | 只用"活到今天"的公司做回测，自动排除了破产退市的，成绩虚高。 |
| **purge / purged split** | 训练/验证/测试三段之间留空白间隔，防止标签的未来视野跨段。 |
| **embargo** | 和 purge 类似的概念，指切分点附近禁用一段数据。 |
| **PIT / Point-in-Time** | "在那个时点真正能拿到的数据"。财务数据必须 PIT 处理。 |
| **早停 / Early stopping** | 训练时看验证集指标，不再改善就停下，防止过拟合。 |
| **best_iter** | 早停选中的最优迭代轮数。**=1 就是模型基本没学到东西。** |
| **过拟合** | 模型把训练集的噪声当规律学进去了，样本外表现差。 |
| **样本外 / OOS** | Out-of-sample，模型训练时没见过的数据。只有样本外成绩才算数。 |
| **换手率** | 每次调仓换掉多少比例的仓位。高换手 = 高摩擦成本。 |
| **回撤 / Drawdown** | 从历史最高点跌下来的幅度。 |
| **Sharpe** | 年化收益 / 年化波动。 |
| **Calmar** | 年化收益 ÷ 最大回撤绝对值。本系统最推荐看的综合指标。 |
| **T+1** | 今天出信号，明天收盘成交（A 股当天买入不能当天卖）。 |
| **一字涨停** | 开盘就涨停且全天没打开，实际买不进去，必须过滤。 |
| **复权 / 后复权 hfq** | 把分红送股的影响还原到价格里，让不同时期的价格可比。**收益/特征用它。** |
| **factor / 复权因子** | `hfq_close / raw_close`。**真实成交价 = `$close / $factor`。** |
| **sleeve / 分仓** | 把资金分成几份，各自独立跑一套逻辑，不做信号融合。 |
| **一手** | A 股最小交易单位 = 100 股。 |
| **manifest** | 冻结模型的"身份证"：SHA256 + config_hash + git commit。 |
| **gain（原生增益）** | 树模型训练时某特征带来的总增益。衡量"模型在关注什么"。 |
| **perm（置换重要性）** | 把某列打乱看指标掉多少。衡量"这个关注有没有价值"。**删特征只能看这个。** |
| **共线性** | 多个特征高度相关（如 STD20/60/120/240）。会稀释单个特征的重要性。 |
| **zscore_mean** | 多个预测各自按日截面 z-score 后取平均。融合多种子/多模型的正确姿势。 |
| **Alpha158** | qlib 内置的 158 个经典量价因子库。 |
| **value_comp** | 本系统的对照策略：EP/BP/CFP/SP 四个估值指标倒数的池内 rank 百分位均值。不用 ML。 |
| **DE / DoubleEnsemble** | qlib 的双重集成模型（样本重加权 + 特征子集）。本系统树模型第一名。 |
| **GATs** | 图注意力网络。Phase B 成绩最高但需要重新验证。 |
